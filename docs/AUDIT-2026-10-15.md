# Аудит Shanyraq — 15 октября 2026

## Вывод и методика

Проект содержит развитое серверное ядро, веб-панель и мобильное приложение. Оценка завершённости относительно PRODUCT_SPEC: **70–80% реализации**, готовности к эксплуатации с реальными жильцами: **50–60%**. Это экспертные диапазоны по завершённости сквозных сценариев, а не процент строк кода или закрытых задач. Наличие SMS, загрузок, камер и доставки уведомлений весит больше количества экранов и CSV-экспортов.

Ориентировочно: backend 80–85%, веб-панель 75–85%, мобильные сценарии 60–70%, внешние интеграции 25–40%. Эти показатели не являются независимыми слагаемыми общей оценки. Уверенность средняя: выполнен обзор исходников и локальные проверки; живые интеграции и развёртывание не проверялись.

Изучены README, PRODUCT_SPEC, PROGRESS, конфигурация CI/контейнеров, авторизация, уведомления, доступ, загрузки, выборочные экраны заявок, голосований, главной и общие компоненты. Это не исчерпывающий аудит безопасности всех endpoint.

## Дизайн и удобство использования

Основа последовательная: нейтральные поверхности, карточки, Lucide-иконки, статусы, общие mobile Button/Input/Badge. Основная работа сейчас — ясность состояний и завершение сценариев, затем визуальная полировка.

1. **Достоверность состояния — P1.** В `frontend-web/src/app/dashboard/layout.tsx` статус «Система онлайн» выводится без проверки доступности. В `frontend-web/src/i18n/locales/ru.json:173` адрес, 140 квартир и площадь зашиты в переводе. Подставлять сведения активного ЖК; состояние соединения выводить по реальному сигналу. Убрать LIVE из неработающего просмотра.
2. **Адаптивность оболочки — P1.** Sidebar имеет постоянные `w-64 shrink-0`; нет мобильного drawer/сворачивания. Верхняя панель и тело имеют фиксированные крупные отступы. На узком экране меню забирает большую часть ширины. Ввести breakpoint, компактный header и отдельную прокрутку меню; проверить 390/768/1440 px.
3. **Навигация — P2.** До 17 одноуровневых пунктов. Разделить на «Работа с жильцами», «Дом и доступ», «Финансы», «Управление»; показывать приоритеты по роли. В GlobalSearch для SUPERADMIN без tenantId молча выбирается первый ЖК — нужен видимый выбор области поиска.
4. **Ошибки и пустые данные — P1.** В mobile Dashboard используются Promise.allSettled, но rejected-результаты не отображаются. Ошибки могут выглядеть как отсутствие заявок/голосований. Разделить loading, empty, error, stale; добавить повтор запроса по блоку. В web GlobalSearch ошибка тоже превращается в пустой результат.
5. **Доступность — P2.** У большинства полей web login label не связан с input через htmlFor/id. Модальное окно заявки — обычный overlay без dialog/aria-modal и явного управления фокусом. Добавить доступные имена, focus trap, Escape и возврат фокуса. Проверить клавиатурой и экранным диктором.
6. **Читаемость — P2.** Таблица заявок использует text-xs, mobile tab labels — 11 px. Основные рабочие данные стоит увеличить, вторичные сведения оставить компактными; предусмотреть крупный системный шрифт. Контраст инструментально не измерялся.
7. **Единый визуальный язык — P2.** Web использует sky/slate, mobile — emerald/gray. Это допустимо как осознанное решение, но общей системы токенов не видно. Определить брендовый акцент, шкалу отступов/радиусов, семантические статусы и типографику. В web вынести повторяющиеся Button/Input/Modal/EmptyState в общие компоненты.
8. **Обратная связь — P2.** В chat/SOS используются browser alert, в гостевых пропусках window.confirm. Унифицировать ошибки, подтверждения и уведомления; сохранять введённые данные при сбое.

Рекомендуемая структура главной: для диспетчера — срочные обращения, просроченные заявки и непрочитанные чаты; для жильца — квартира, основные действия, требующие внимания события. SOS оставить заметным и защищённым от случайного нажатия; текущий компонент удержания — полезная основа.
