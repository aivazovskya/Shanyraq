# 0100 — Сценарий диспетчера в карточке заявки

Дата: 2026-10-16.

## Реализовано

- Переход с главной по точному ID в q сразу открывает карточку соответствующей заявки. Закрытая карточка не открывается повторно от фонового обновления списка.
- Выбор ответственного сотрудника через GET /service-requests/:id/assignees. Выдаются только активные HOA_ADMIN/DISPATCHER из ЖК заявки, с минимальным набором полей (ID, имя, фамилия, роль).
- Сервер повторно проверяет сотрудника при назначении: существование, активность, роль и принадлежность ЖК. Подмена ID сотрудника другого ЖК отклоняется.
- Отдельной роли мастера в текущей модели нет. Назначение выполняется среди существующих сотрудников, которые имеют доступ к работе с заявками; новый тип аккаунта этим изменением не вводился.
- Новая заявка при назначении переходит в ASSIGNED. Действия веб-карточки зависят от текущего статуса: начать работу, отметить выполнение, закрыть, отклонить, вернуть в работу или открыть повторно. Начало работы в вебе требует ответственного; закрытие и отклонение требуют подтверждения.
- Публичный ответ явно помечен как видимый жителю. Существующие внутренние заметки отмечаются отдельно. Ошибка доставки уведомления после сохранения статуса/комментария не возвращает ошибку сохранения и не провоцирует повторную отправку.
- Председатель ОСИ не получает элементы смены статуса и назначения; service-проверка приведена к ролям controller (DISPATCHER, HOA_ADMIN, SUPERADMIN).
- Смена статуса/ответственного и событие истории записываются одной Prisma-транзакцией в существующий AuditLog. Миграция БД не требуется.
- История возвращается только после проверки доступа к заявке; выборка ограничена tenantId, targetType/targetId и действиями REQUEST_STATUS_CHANGED/REQUEST_ASSIGNEE_CHANGED. В истории — время, сотрудник, статусы и новый ответственный. Начальная запись о создании строится из createdAt. Ранее не зафиксированные изменения не восстанавливаются и не выдумываются.
- Оценка жителя с закрытием заявки тоже фиксируется в истории.
- expectedUpdatedAt из веб-карточки и условное обновление по updatedAt защищают от потери изменений другого сотрудника; конфликт возвращает код SERVICE_REQUESTS.UPDATE_CONFLICT (409).
- Фотографии отображаются миниатюрами, полные изображения/документы открываются отдельно; недоступный предпросмотр предлагает открыть файл. Разрешены только HTTP(S)-ссылки без встроенных credentials. Права S3 и способ доставки приватных файлов этим этапом не менялись.
- Новые сообщения и ошибки переведены на ru/kk/en (ошибки также в mobile).

## Совместимость

Набор действий ограничен в веб-интерфейсе. Сервер сохраняет существующий контракт переходов по enum для совместимости с мобильными клиентами, дополненный валидацией назначения и необязательной проверкой версии. Общая строгая машина переходов для всех клиентов этим этапом не вводилась.

## Проверки

- Полный backend Jest: 43 набора / 879 тестов успешно на версии до последнего дополнительного теста устаревшей карточки.
- Добавлены тесты назначения в чужой ЖК, неактивного сотрудника, недопустимой роли/пустого ID, прав председателя, атомарной записи истории, ошибки истории, конфликта, повторного сохранения и сбоя уведомлений.
- Есть сервисная проверка последовательности назначение → работа → публичный ответ → выполнение → закрытие с историей (моки Prisma/уведомлений; не интеграционный запуск настоящей БД).
- Frontend: 5 проверок набора действий и безопасных URL вложений — успешно; команда npm run test:requests добавлена в CI.
- Финальный целевой прогон ServiceRequestsService: 36/36 тестов успешно, включая защиту устаревшей карточки. Сборка backend и финальный frontend typecheck также успешны.
- Production-сборка веба успешно завершена, сгенерировано 26 страниц.
- Визуальная приёмка на телефоне/desktop и работа с реальными файлами/аккаунтами не проверялись: ранее доступ к локальной странице был отклонён политикой браузерного инструмента. Ограничение не обходилось.
