# 0101 — Приёмка диспетчерского сценария на настоящей инфраструктуре

Дата: 2026-10-16. Результат: **PASS, 9 контрольных этапов**.

## Окружение

Для запуска использован отдельный Compose-проект `shanyraq-dispatcher-e2e`:

- PostgreSQL 16 — 127.0.0.1:55432, отдельная БД `shanyraq_dispatcher_e2e`.
- Redis 7 — 127.0.0.1:56379.
- MinIO — 127.0.0.1:59000, отдельные приватные бакеты.
- Настоящий Nest AppModule слушает случайный порт только на 127.0.0.1, с JWT, role guards, DTO validation, Prisma и Redis throttling.

Созданы только синтетические аккаунты/данные: житель, два диспетчера, председатель и диспетчер другого ЖК. Пароли и ключи генерируются при запуске и не выводятся. Тестовый файл — PNG 1×1. Исходный seed с удалением таблиц не использовался, существующая БД проекта не изменялась.

SMS-транспорт — специально ограниченный NODE_ENV=test: OTP создаётся/проверяется настоящим AuthService и хранится в Redis, без отправки внешнего SMS. Push на устройство не проверяется; проверены записи уведомлений в БД и их чтение жителем через HTTP.

## Пройдено через HTTP

1. Применение настоящих Prisma migrations к изолированной БД.
2. Вход сотрудников по паролю и вход жильца по OTP с настоящим Redis.
3. Загрузка файла в настоящий S3/MinIO и создание заявки верифицированным собственником.
4. Список исполнителей только своего ЖК; запрет назначения чужого сотрудника, доступа другого ЖК и изменения статуса председателем.
5. Назначение → начало работы → конфликт устаревшей карточки → публичный ответ → внутренняя заметка. Житель видит ответ, но не видит внутреннюю заметку.
6. Уведомления жителя сохранены в PostgreSQL и доступны через API.
7. Выполнение → закрытие; возвращаемая история содержит ASSIGNED, IN_PROGRESS, RESOLVED, CLOSED и правильного исполнителя.
8. Житель и второй диспетчер читают исходные байты фото через авторизованный API; MIME image/png, private/no-store; анонимный/чужой доступ запрещён; прямой S3 URL по-прежнему возвращает 403.
9. Копирование чужого приватного S3 URL в собственную заявку не предоставляет доступ к объекту.

## Найдено и исправлено

Первый содержательный прогон прошёл бизнес-сценарий, но чтение фото со второго клиента вернуло **403**: клиент получал URL приватного S3 без способа авторизованного чтения.

Добавлен `GET /service-requests/:id/attachments/:attachmentId`. Он проверяет доступ к заявке и принадлежность вложения, затем читает объект через S3 SDK. Произвольные URL не становятся сетевыми запросами. Поддерживаются только известные origins, бакеты и ключи загруженных файлов.

Загрузка помечает объект серверной metadata `uploader-id`; в presigned POST значение фиксируется подписанным условием. Чтение требует совпадения владельца объекта с создателем заявки, что предотвращает подмену чужого URL. Веб-карточка получает файл с Bearer token и показывает временный Blob URL, отменяет запросы и освобождает Blob URL при закрытии.

Старые файлы без metadata владельца этот защищённый маршрут не открывает. Их восстановление требует отдельной проверки/миграции происхождения; автоматическое присвоение владельца по произвольной сохранённой ссылке не выполняется. Остальные модули медиа и мобильный просмотр вложений этим этапом не переведены на новый маршрут.

## Повторный запуск

Из корня репозитория:

```powershell
docker compose -f backend/test/compose.dispatcher-e2e.yml up -d --wait --wait-timeout 90
cd backend
npm run build
npm run test:dispatcher:live
cd ..
docker compose -f backend/test/compose.dispatcher-e2e.yml down --volumes
```

Runner отказывается работать при внешнем DATABASE_URL в окружении или NODE_ENV=production, сам задаёт только изолированные адреса. Перед запуском очищает исключительно Redis отдельного тестового контейнера на порту 56379, чтобы прежние попытки не расходовали лимиты следующего запуска. Параллельно в одной машине этот runner не запускать.

В CI добавлены запуск окружения, HTTP-приёмка и always-cleanup после backend build.
