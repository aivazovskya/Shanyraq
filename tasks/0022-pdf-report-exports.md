# Task 0022: PDF report exports (ОСС protocol + personal account statement)

**Status:** Completed
**Assignee:** Antigravity
**Reviewer:** Team lead (architecture review only, no direct code changes)

## Context

Beyond-ТЗ feature #3. While auditing the votings module for
[Task 0021](0021-scheduled-charge-generation.md)'s context, a real gap
surfaced: `VotingsService.closeMeetingAndGenerateProtocol`
([votings.service.ts:288](../backend/src/modules/votings/votings.service.ts))
already creates a `MeetingProtocol` record with a `pdfUrl` field — but
that URL is **entirely fake**, hardcoded as
`` `https://storage.shanyraq.kz/protocols/${protocolNumber}.pdf` `` with
no PDF ever generated or uploaded. Given this ТЗ point is explicitly about
a legally-meaningful document (ОСС decisions, per the already-accepted
HMAC+OTP-instead-of-ЭЦП tradeoff in [PROGRESS.md](PROGRESS.md)'s open
questions), a protocol that claims to have a `pdfUrl` but 404s if anyone
actually opens it is worse than not having the field at all. This task
fixes that and adds a second, related export: a downloadable statement
PDF for a resident's personal account.

### Architecture decisions already made — do not re-litigate

1. **`pdfkit`, not a headless-browser HTML-to-PDF pipeline.** No
   Puppeteer/Playwright — this app doesn't need arbitrary HTML rendering,
   just two structured documents with tables and text, and a Chromium
   dependency is a heavy, fragile addition to a Docker image for that.
   `pdfkit` generates PDFs programmatically and is the standard choice for
   this in the Node ecosystem.
2. **Bundle a real Unicode/Cyrillic TTF font — this is the #1 way this
   kind of task goes wrong.** `pdfkit`'s built-in fonts (Helvetica, Times)
   do **not** support Cyrillic at all — text will render as blank boxes or
   throw. Bundle an open-license TTF (e.g. **Roboto** or **DejaVu Sans**,
   both fully open-license and support Cyrillic) under
   `backend/src/assets/fonts/`, register it with `doc.registerFont(...)`,
   and use it for every string in both documents. **Verify this by
   actually opening a generated PDF and confirming Cyrillic text renders
   correctly** — a test asserting the PDF buffer is non-empty does NOT
   catch a missing-glyph/blank-box failure.
3. **A small shared PDF-building helper, not two independent
   implementations.** Put shared setup (font registration, page margins,
   header/footer style) in one place — e.g.
   `backend/src/common/pdf/pdf-document.helper.ts` — that both the
   protocol and statement generators use, so the two documents look
   visually consistent and any later change to house style (logo, footer
   text) happens in one place.
4. **Protocol PDF: generate once at close-time, upload to S3, store the
   real URL — same as today's persistence model, just make the URL
   real.** Reuse the existing S3/MinIO storage from
   [uploads.service.ts](../backend/src/modules/uploads/uploads.service.ts)
   (either call its `uploadFile` with a synthetic
   `Express.Multer.File`-shaped object carrying the generated buffer, or
   use the same underlying S3 client directly — your call, whichever is
   cleaner) into the existing `shanyraq-documents` bucket.
   `application/pdf` is already in [Task 0019](0019-security-hardening.md)'s
   `ALLOWED_MIME_TYPES` allowlist, so no allowlist change is needed.
5. **Statement PDF: generate on-demand, stream the response, don't
   persist it.** Unlike the protocol (a single canonical legal document
   generated once), a resident might request a statement for any
   month/period repeatedly — there's no reason to store every generated
   copy in S3. Generate the buffer per-request and return it directly as
   the HTTP response (`Content-Type: application/pdf`,
   `Content-Disposition: attachment; filename=...`).
6. **Reuse existing authorization, don't write new checks.** The protocol
   already only gets generated by whoever can call `closeMeeting` (staff
   role gate already in place). The statement endpoint must reuse
   `FinanceService.getAccountById`'s existing authorization (verified
   owner of the unit, or staff of the matching tenant) — call that method
   to fetch the data, don't duplicate its authorization logic.

## Subtask A — Shared PDF infrastructure

- Add `pdfkit` (and `@types/pdfkit` as a dev dependency) to
  `backend/package.json`.
- Add a Cyrillic-capable TTF font file under `backend/src/assets/fonts/`
  (check its license is compatible with this project — Roboto and DejaVu
  Sans are both fine, Google Fonts / DejaVu's own license respectively).
- Create the shared helper from decision #3 — common page setup, font
  registration, a reusable "title + subtitle" header block and a simple
  table-drawing utility (both documents need at least one table: agenda
  items with vote tallies for the protocol, charges/payments rows for the
  statement).

## Subtask B — Real ОСС protocol PDF

In `VotingsService.closeMeetingAndGenerateProtocol`:
- After closing the meeting, build the protocol document: meeting title,
  tenant/ЖК name, protocol number, date, quorum percentage, and for each
  agenda item — the question, decision type (simple majority / 2/3
  supermajority), area-weighted FOR/AGAINST/ABSTAIN breakdown (already
  computed in `enrichMeetingWithResults`), and the approved/rejected
  result.
- Upload the generated PDF (decision #4) and store the **real** returned
  URL in `MeetingProtocol.pdfUrl`, replacing the hardcoded fake string.

**Test:** closing a meeting produces a `MeetingProtocol` whose `pdfUrl`
comes from the actual upload call (mock the upload in the test, assert
the service passes it a non-empty PDF buffer and that the returned URL is
used, not a hardcoded string).

## Subtask C — Personal account statement PDF

- Add `GET /finance/accounts/:accountId/statement?month=X&year=Y` to
  [finance.controller.ts](../backend/src/modules/finance/finance.controller.ts).
  If `month`/`year` are omitted, generate a statement covering all
  charges/payments on the account (no period filter) — your call on
  whether that's the sensible default or whether requiring the query
  params outright is cleaner; either is fine as long as it's validated,
  not silently wrong.
- Call `FinanceService.getAccountById` (decision #6) to get the data and
  enforce authorization, then filter charges/payments to the requested
  period if given.
- Build the statement PDF: account number, unit/building info, period,
  opening reference, a table of charges (tariff name, amount, date) and a
  table of payments (amount, date, recorded by), and the resulting
  balance.
- Stream the PDF directly as the response (decision #5).

**Test:** a verified owner can download their own account's statement; a
resident who isn't a verified owner of that account gets the same
`FINANCE.ACCOUNT_ACCESS_CONFIRMED_ONLY` rejection `getAccountById`
already produces (i.e. don't let this new endpoint accidentally bypass
existing authorization); staff of the matching tenant can download it too.

## Acceptance criteria

- Opening a real generated PDF (both protocol and statement) in a PDF
  viewer shows correctly rendered Cyrillic text — describe in the PR how
  you verified this (e.g. saved a sample output and opened it, or a
  screenshot).
- `MeetingProtocol.pdfUrl` is a real, working URL to an uploaded document
  after a meeting is closed — no more hardcoded fake URLs anywhere in
  this codebase (`grep` for the old pattern to confirm it's gone).
- The statement endpoint enforces the exact same authorization as
  `getAccountById` — verified via a rejection test, not just a happy-path
  test.
- All existing backend tests for `votings` and `finance` still pass.
- `npm test` passes in `backend/`; `npx tsc --noEmit` clean.
- No frontend/mobile UI changes required for this task — a plain
  "download" link/button pointing at the new endpoint on the existing
  account-detail page is a reasonable small addition if you want to make
  the feature actually reachable from the UI, but the core deliverable is
  the backend PDF generation. If you do add a UI entry point, keep it
  small and use `t()` for any new label with full kk/ru/en parity.

## Explicitly out of scope

- Any other export (analytics CSV/Excel, service-request history, etc.)
  — this task is scoped to exactly the two documents above.
- Digital signing of the protocol PDF (ЭЦП) — already an accepted,
  deliberate tradeoff per [PROGRESS.md](PROGRESS.md)'s open questions,
  not something to revisit here.
- Redesigning how `enrichMeetingWithResults` or `getAccountById` compute
  their data — this task only renders existing data into a PDF.
- Localizing the PDF content itself into kk/en — these are formal
  Russian-language legal/financial documents by convention in this
  codebase (matching how backend `message` fields and push-notification
  bodies are also Russian-only); only UI labels around them (if any get
  added) need i18n.

## Review addendum (2026-09-09) — accepted, no issues found

**Cyrillic rendering independently verified beyond what the automated
tests check** (decision #2's explicit concern): the bundled
`DejaVuSans.ttf`/`DejaVuSans-Bold.ttf` are real, valid TTF files (correct
`00 01 00 00` magic bytes, ~700-757KB, matching genuine DejaVu Sans sizes
— not placeholders). Using `fontkit` (pdfkit's own font-parsing
dependency) directly, checked every unique character actually used across
both documents' real content — Russian Cyrillic, Kazakh-specific letters
(ң/ғ/қ from "Шаңырақ"), the ₸ tenge sign, guillemets, em-dash — against
the font's glyph table: **all 50 unique characters resolved to real
glyphs, zero `.notdef` fallbacks.** This is a stronger check than visual
inspection (it directly answers "will this render as a box or a real
glyph" rather than trusting a screenshot at one zoom level).
`nest-cli.json` was correctly updated with `"assets": ["assets/**/*"]` —
without this, the font files would silently fail to copy into `dist/` on
a real production build despite working fine in dev/jest, which is
exactly the kind of prod-only failure decision #2 was worried about.

**Protocol PDF (Subtask B):** every field read in `buildMeetingProtocolPdf`
(`quorum.totalEligibleArea/totalVotedArea/quorumPercent/isQuorumAchieved`,
`item.results.forPercentFromVoted/areaAgainst/areaAbstain/isApproved`)
verified against `enrichMeetingWithResults`'s actual return shape —
no field-name mismatches that would silently print `undefined`/`0`
into a legal document. The old hardcoded fake `pdfUrl` is confirmed
completely removed (`grep` for the old pattern: zero matches anywhere).
Test proves the buffer passed to `uploadsService.uploadFile` has real
`%PDF-` magic bytes, not a stub.

**Statement PDF (Subtask C):** correctly calls `getAccountById` first to
enforce authorization exactly as scoped — verified via a rejection test
(non-owner resident gets `FINANCE.ACCOUNT_ACCESS_CONFIRMED_ONLY`), not
just a happy-path test. `@Roles` on the new controller endpoint
(`HOA_ADMIN`/`SUPERADMIN`/`HOA_CHAIRMAN`/`RESIDENT_OWNER`) matches
`getAccountById`'s actual staff/owner-only logic exactly — correctly
excludes `DISPATCHER`/`SECURITY` (not staff per that method) and
`RESIDENT_TENANT` (renters don't own the account), rather than a generic
copy-pasted role list. Filename construction uses only server-controlled
data (DB `accountNumber`, `parseInt`-derived period numbers) — no
`Content-Disposition` header-injection surface from user input.

279/279 backend tests pass, `tsc --noEmit` clean, `UploadsModule`
correctly imported into `VotingsModule` for the new DI dependency. No
frontend/mobile changes were made (acceptable per the task's own scope
note — the backend PDF generation was the core deliverable). Task
accepted, no fixes required.
