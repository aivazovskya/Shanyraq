## Context

Заказчик (ОСИ/КСК) просит, чтобы Shanyraq перекрыл всё, что сейчас делает
команда аналитиков вручную в Excel при проверке деятельности председателя
ОСИ. Исходный запрос заказчика (суть):

1. Документы из папки «расходы» перенести в таблицу → видеть расходы по
   месяцам и кварталам.
2. Запросить у бухгалтера выгрузку из 1С за год: зарплаты и 7 налогов.
3. Запросить у двух УК расшифровку крупных сумм (детальные данные только у
   них). Этот пункт самый спорный.
4. Данные Алсеко: начисления и оплаты по месяцам за год.
5. Выписка Kaspi Bank (через неё председатель принимает оплаты жителей и
   видит поступления).
6. «Левая сторона» — бюджет (его готовит заказчик), «правая» — фактические
   расходы. Объединить по месяцам → найти перерасход и места оптимизации.

Цель задачи: всё это должно жить в приложении, чтобы ответственный состав
ОСИ/КСК и жители могли строить отчёты сами, без ручного Excel.

### Решения, которые нужно принять до старта (см. «Открытые вопросы»)

Решения ниже — рекомендации по умолчанию; менять только по согласованию.

1. **Интеграции — в объёме (решение заказчика).** Заказчик сверяет данные
   и принципиально не доверяет одному источнику, поэтому каждый внешний
   источник (1С, Алсеко, Kaspi, УК) подключается как **коннектор** и
   сверяется с остальными. Файловый импорт (Excel/CSV) остаётся как
   резервный канал и как способ первой загрузки, но не заменяет
   интеграцию. См. раздел «Интеграции и multi-source сверка» ниже.
2. **Реальный `.xlsx` на вход и выход.** Для импорта нужен парсер xlsx,
   для итогового отчёта — многолистовая книга (бюджет / факт / план-факт /
   сверка). Добавить `exceljs` (одна зависимость, и чтение, и запись).
   Это пересматривает Task 0032 decision #2 — там CSV хватало для
   одиночной таблицы, здесь нужны листы и формулы.
3. **Импорт всегда в два шага: загрузка → предпросмотр → подтверждение.**
   Данные не попадают в базу, пока человек не увидел и не принял строки
   с ошибками/дубликатами. Каждый импорт — запись `ImportBatch`, которую
   можно откатить целиком (void всех строк партии).
4. **Ничего не удаляется.** Откат = void (как у `Expense`), с причиной и
   записью в `AuditLog`.
5. **Деньги в тенге, `Float` как в остальной схеме** (согласовано с
   текущими моделями; переход на `Decimal` — отдельная задача).
6. **Доступ:** загрузка/импорт/правка — `HOA_ADMIN`, `SUPERADMIN`;
   просмотр сводок — плюс `HOA_CHAIRMAN`. Жители видят только
   агрегированный отчёт прозрачности (существующий), не сырые выписки:
   выписка Kaspi и 1С содержат персональные данные.
7. **ПДн:** банковская выписка и зарплаты содержат ФИО, ИИН, суммы.
   Хранить только то, что нужно для сверки (дата, сумма, назначение,
   контрагент/плательщик, ссылка на квартиру); ИИН — только как
   `iinHash`, по образцу `User` ([schema.prisma](../backend/prisma/schema.prisma)).
   Файлы-источники хранить в S3 (бакет документов) с доступом только staff.

## Блок 1 — Импорт документов расходов → таблица

**Цель:** перенести папку «документов/расходов» в журнал расходов
массово и видеть месяцы/кварталы.

### Backend

- Расширить `Expense` (миграция, все поля nullable → обратно совместимо):
  `counterparty String?`, `documentNumber String?`, `source` enum
  (`MANUAL | IMPORT_EXCEL | IMPORT_1C | IMPORT_UK`), `importBatchId String?`,
  `periodMonth/periodYear Int?` (период начисления, если отличается от
  даты оплаты), `attachmentUrl String?`.
- Новая модель `ImportBatch`: `id, tenantId, kind (EXPENSES | ONEC_PAYROLL |
  UK_DETAIL | ALSECO | BANK_STATEMENT), fileName, fileUrl, status
  (PREVIEW | APPLIED | VOIDED), rowsTotal, rowsApplied, rowsSkipped,
  createdById, createdAt, voidedAt/voidedById/voidedReason`.
- Эндпоинты (`finance/imports`):
  - `POST tenants/:tenantId/imports/expenses/preview` — multipart xlsx/csv,
    возвращает распознанные строки, ошибки по строкам, подозрение на
    дубликаты (дата + сумма + контрагент + номер документа).
  - `POST imports/:batchId/apply` — применить принятые строки.
  - `POST imports/:batchId/void` — откатить партию целиком.
  - `GET imports/templates/expenses.xlsx` — шаблон Excel с примером и
    справочником категорий.
- Маппинг колонок: автоопределение по заголовкам (дата, сумма, статья,
  контрагент, описание) + возможность ручного маппинга в UI.
- Категории: нормализация к существующим `Expense.category`; новые
  категории создаются только после подтверждения в предпросмотре.
- Вложения: `POST expenses/:id/attachment` (PDF/JPG/PNG, лимит из
  существующего `uploads`-модуля, S3 бакет документов). Заказчик сказал
  «фотографий не надо», значит вложения — **необязательны**; нужны только
  для тех документов, которые захотят приложить.

### Web

- Страница `dashboard/finance/imports`: загрузка файла, таблица
  предпросмотра (ошибки красным, дубликаты жёлтым, чекбокс «пропустить»),
  кнопка «Применить», история партий с откатом.
- `dashboard/finance/expenses`: фильтр по партии/источнику, группировка
  «по месяцам / по кварталам» с итогами (клиентская агрегация по
  `expenseDate`, серверный эндпоинт сводки — в Блоке 5).

### Тесты

- Парсинг xlsx с кириллицей и разными форматами даты/суммы
  (`1 234,50`, `1234.5`, `01.03.2026`, serial date Excel).
- Дубликаты не создаются повторно при повторной загрузке того же файла.
- Откат партии void-ит все её расходы и не трогает остальные.
- Мульти-тенантность: нельзя применить/откатить чужую партию.

## Блок 3 — Расшифровка крупных сумм (две УК)

**Цель:** крупная сумма, которая в журнале одна строка («оплата УК —
2 400 000 ₸»), раскрывается в детали, которые присылает УК. Заказчик
отметил это как самый спорный пункт — поэтому важна прозрачность и
след изменений.

- Модель `ExpenseBreakdownLine`: `expenseId, lineNo, description, category?,
  quantity?, unitPrice?, amount, source (UK_DOCUMENT), importBatchId`.
- Инвариант: сумма строк расшифровки **не обязана** равняться сумме
  расхода — вместо блокировки показывается **расхождение**
  (`expense.amount − Σ lines`) и статус `полностью / частично / не
  расшифровано`. Это и есть главный индикатор для аудита.
- Привязка к УК: в `Tenant` не нужна новая сущность; добавить
  справочник `ManagementCompany` (`tenantId, name, bin?`) и поле
  `Expense.managementCompanyId?`, чтобы фильтровать «всё, что проходит
  через УК №1 / УК №2».
- Импорт: `imports/uk-detail/preview|apply|void`. В файле УК одна колонка
  указывает, к какому расходу относится строка (номер документа или
  дата+сумма); предпросмотр показывает **автосопоставление** и
  нераспознанные строки, которые вручную привязываются к расходу.
- Web: на карточке расхода — раскрывающаяся расшифровка, бейдж статуса,
  отдельный отчёт «Не расшифровано» — список расходов выше порога
  (настраиваемый, по умолчанию 100 000 ₸) без полной расшифровки, по
  убыванию суммы. Это готовый список вопросов к УК.
- Запрос к УК: кнопка «Сформировать запрос в УК» — Excel со списком
  нерасшифрованных расходов (дата, документ, сумма) для отправки УК.
  Отправка вне приложения (почта) — приложение ничего не рассылает.

**Тесты:** расхождение считается верно при частичной расшифровке;
void расхода каскадно скрывает его расшифровку; строки нельзя привязать
к расходу чужого тенанта.

## Блок 4 — Алсеко (начисления/оплаты) и выписка Kaspi

**Цель:** сверить, что жители реально заплатили, что получила
председатель и куда ушло — выявить долги по Алсеко и оплаты «не с тех
статей».

### 4a. Алсеко

- Модель `UtilityStatementLine`: `tenantId, importBatchId, provider
  (ALSECO), periodMonth, periodYear, serviceName, accrued, paid,
  accountRef?` (лицевой счёт в Алсеко / квартира, если есть), `createdAt`.
- Импорт `imports/alseco/preview|apply|void` + шаблон.
- Сводка «Алсеко по месяцам»: начислено, оплачено, долг нарастающим
  итогом, по каждой услуге (по пунктам — как просит заказчик).

### 4b. Выписка Kaspi

- Модель `BankTransaction`: `tenantId, importBatchId, bank (KASPI),
  txDate, amount, direction (IN | OUT), counterparty?, purpose?,
  payerIinHash?, matchedUnitId?, matchedExpenseId?, matchStatus
  (UNMATCHED | AUTO | MANUAL | IGNORED)`.
- Импорт `imports/bank/preview|apply|void`. Парсер под формат выписки
  Kaspi (xlsx/csv) — **нужен реальный образец выписки от заказчика**, до
  получения образца делаем маппинг колонок вручную.
- Сверка:
  - `IN` → квартира/лицевой счёт по ИИН-хешу, номеру квартиры в
    назначении, ФИО (нечёткий матч); подтверждённые создают `Payment`
    (расширить `PaymentMethod`: `+ BANK_IMPORT`, `recordedById` —
    импортирующий).
  - `OUT` → расход (`Expense`) по дате/сумме/контрагенту; несовпавшие
    исходящие выводятся отдельным списком «Выплаты без документа» —
    ключевой индикатор для аудита председателя.
- Отчёт «Оплаты не с тех статей»: сравнение `назначение платежа` и
  статьи расхода/начисления; помечает платежи, ушедшие на другую
  статью, чем начислено.
- Приватность: экран сверки только `HOA_ADMIN`/`HOA_CHAIRMAN`/`SUPERADMIN`;
  в API ответ без сырого ИИН; файл-источник в закрытом S3-бакете.

**Тесты:** автосопоставление по ИИН-хешу и номеру квартиры; повторная
загрузка пересекающейся выписки не создаёт двойные `Payment`
(идемпотентность по `date+amount+counterparty+purpose` хешу строки);
баланс лицевого счёта пересчитывается после применения (используем
существующий `personal-account.helper.ts`, **не пишем баланс вручную**).

## Блок 5 — Бюджет и сводка план/факт по месяцам

**Цель:** «левая сторона» (бюджет, готовит заказчик) + «правая»
(факт из блоков 1–4) → одна таблица по месяцам, видно перерасход и где
оптимизировать.

- Модель `BudgetLine`: `tenantId, year, month (1–12), category,
  plannedAmount, note?, importBatchId?`, `@@unique([tenantId, year, month,
  category])`. Ввод вручную в таблице + импорт Excel
  (`imports/budget/preview|apply|void`, шаблон: категории в строках,
  12 месяцев в колонках — привычный для заказчика вид).
- Сервис сводки `GET finance/tenants/:tenantId/budget-vs-actual?year=`:
  по каждой категории и месяцу — `planned`, `actual`, `delta`,
  `delta%`; нарастающим итогом; агрегаты по кварталам и за год.
  Источники факта: `Expense` (не void), `PayrollEntry` (статья
  «Зарплата и налоги»), с пометкой доли нерасшифрованных крупных сумм
  (из Блока 3) — чтобы цифра не выглядела более надёжной, чем есть.
- Правая часть, «где можно оптимизировать»: топ категорий по
  абсолютному и относительному перерасходу, категории без бюджета,
  месяцы-выбросы (факт > среднего × порог).
- Поступления рядом с расходами: начислено (`Charge`), оплачено
  (`Payment`), Алсеко (4a), банковские `IN` (4b) — для картины
  «денег пришло / ушло» по месяцам.
- Web: `dashboard/finance/budget` (таблица бюджета, редактирование,
  импорт) и `dashboard/finance/audit` — главная сводка: месяцы × категории,
  цветовая индикация перерасхода, переключатель месяц/квартал/год,
  drill-down в расходы и расшифровку.
- Экспорт: `GET .../audit/export.xlsx` — многолистовая книга: «Бюджет»,
  «Факт», «План-факт», «ФОТ и налоги», «Алсеко», «Сверка банка»,
  «Не расшифровано». Заказчик сможет открыть её рядом со своим Excel.
- Жителям: в существующий отчёт прозрачности добавить блок план/факт
  **на уровне категорий и месяцев** (без контрагентов и выписок) — только
  если председатель включит публикацию (настройка тенанта, по умолчанию
  выключена).

**Тесты:** план/факт и кварталы считаются верно на фикстуре из 12 месяцев;
void-нутые расходы не попадают в факт; категории без бюджета и без
факта обрабатываются; экспорт xlsx открывается и содержит все листы с
кириллицей.

## Интеграции и multi-source сверка

**Принцип:** ни один источник не является истиной. Приложение хранит данные
каждого источника отдельно, с пометкой происхождения, и **сравнивает их
между собой**; расхождения — главный результат, а не побочный эффект.

### Архитектура коннекторов

- Общий интерфейс `SourceConnector` (`kind`, `testConnection()`,
  `fetch(period)` → нормализованные записи) и таблица `DataSource`
  (`tenantId, kind (ONEC | ALSECO | KASPI | UK), mode (API | FILE),
  encryptedCredentials, lastSyncAt, lastStatus, lastError`).
  Учётные данные — только в зашифрованном виде (тот же AES-GCM, что для
  ПДн, ключ из окружения), никогда в ответах API и логах.
- Синхронизация: ручной запуск + плановая (cron, по образцу
  `finance-scheduler.service.ts`, Task 0021), идемпотентная: повторный
  заход за тот же период обновляет записи, а не дублирует (ключ —
  внешний id источника, при его отсутствии хеш строки).
- Каждая синхронизация — `SyncRun` (период, количество строк, ошибки,
  кто/что запустило) → виден в аудит-логе и на странице «Источники».
- Сырой ответ источника сохраняется (S3, закрытый бакет) для
  доказательности: спор «а что вернула 1С» решается файлом, а не словом.
- Режим `FILE` использует те же нормализаторы, что и `API`, поэтому
  если у источника нет доступного API, он подключается файлом без
  изменения остальной системы.

### Источники и реалистичность API (**проверить до старта**, не предполагать)

| Источник | Что нужно | Предполагаемый канал | Риск |
|---|---|---|---|
| 1С (зарплата, налоги, расходы) | ФОТ + 7 налогов, расходы, контрагенты | HTTP-сервис / OData 1С (если опубликован и есть доступ) | нужен доступ и публикация на стороне бухгалтера/хостинга 1С; конфигурация 1С у ОСИ неизвестна |
| Алсеко | начисления и оплаты по услугам и месяцам | неизвестно: публичный API не подтверждён | может оказаться только кабинет/выгрузка → `FILE` |
| Kaspi (выписка председателя) | входящие/исходящие платежи | неизвестно: **личный** счёт физлица, публичного API для выписки частного счёта может не быть | возможно только выписка/PDF/Excel → `FILE`; плюс юридические ограничения |
| УК №1, УК №2 | расшифровка крупных сумм | почти наверняка файлы/портал | `FILE` |

Для каждого источника первым делом — **спайк**: выяснить, существует ли
легитимный способ доступа, кто его даёт и как получить согласие владельца
счёта/базы. Где API нет, не обходим защиту и не сохраняем чужие пароли от
банка или кабинета: режим `FILE` остаётся основным.

### Сверка между источниками (ядро ценности)

Новая модель `ReconciliationCheck` / `ReconciliationIssue`
(`tenantId, period, type, severity, sourceA, sourceB, expected, actual,
delta, status (OPEN | EXPLAINED | RESOLVED), explanation, resolvedById`).
Типовые проверки:

1. **Начислено жителям ↔ Алсеко:** начисления в Shanyraq/Алсеко против
   оплат у Алсеко по месяцам и услугам.
2. **Оплаты жителей (Shanyraq `Payment`) ↔ поступления Kaspi `IN`:** кто
   заплатил, но не отражён; поступление без квартиры.
3. **Выплаты Kaspi `OUT` ↔ расходы/1С:** выплата без документа; расход без
   выплаты; сумма не совпала.
4. **ФОТ в 1С ↔ выплаты зарплаты в банке ↔ журнал расходов:** сходится ли
   «на руки» и налоги, нет ли дублирования.
5. **Расход ↔ расшифровка УК:** расхождение суммы и состава (Блок 3).
6. **Бюджет ↔ факт по всем источникам** (Блок 5).

Каждая проверка запускается по периоду, результат — список расхождений с
суммой и ссылками на строки обоих источников; статус «объяснено» требует
текстовое пояснение и фиксируется в `AuditLog`. Дашборд «Источники и
сверка»: по каждому источнику — актуальность (`lastSyncAt`), количество
открытых расхождений, сумма под вопросом.

### Допуски и спорные случаи

- Допуск сопоставления настраивается (по умолчанию точное совпадение
  суммы; дата ± 3 дня; нечёткое сравнение контрагента) и **всегда виден**
  в отчёте — чтобы сверка была воспроизводимой.
- Расхождение не «исправляется» автоматически и не подгоняет данные
  одного источника под другой.

### Влияние на блоки 2–4

- **Блок 2 (1С):** режим `API` (OData/HTTP-сервис) приоритетен, `FILE` —
  резерв и шаблон. Подтвердить у бухгалтера версию/конфигурацию 1С.
- **Блок 3 (УК):** сопоставление строк расшифровки — через сверку №5.
- **Блок 4 (Алсеко, Kaspi):** коннекторы + сверки №1–4; импорт файлов —
  тот же нормализатор.

## Порядок работ и зависимости

1. Общая основа: `exceljs`, `ImportBatch`, парсер/превью, void партии,
   шаблоны, аудит-лог, права (Блок 1 включает это как фундамент).
2. Блок 1 (расходы) → Блок 5 (бюджет, сводка) — первый осязаемый
   результат для заказчика: «увидеть картину по месяцам».
3. Блок 2 (1С) и Блок 3 (УК) — параллельно, зависят только от основы.
4. Блок 4 (Алсеко, Kaspi) — последним: нужен образец выписки; самый
   рискованный по ПДн и самый объёмный по сопоставлению.
5. **Спайки по интеграциям — параллельно с шагом 1** (по сути, не код, а
   выяснение доступа): 1С, Алсеко, Kaspi, УК. Результат определяет, какие
   коннекторы будут `API`, а какие `FILE`.
6. Слой сверки и дашборд «Источники и сверка» — после появления хотя бы
   двух источников с данными (первыми — журнал расходов + 1С/выписка).

## Что нужно от заказчика (не код)

- Файл бюджета в текущем виде (структура категорий и месяцев).
- Перечень документов расходов (форматы: xlsx/pdf/сканы?) и порог
  «крупной суммы».
- Расшифровки от двух УК (или хотя бы форматы, в которых они их дают).
- Подтверждение юридической стороны: кто вправе загружать выписки с
  ПДн жителей в систему.

## Открытые вопросы

0. **Доступ к источникам (блокер для интеграций):** есть ли у ОСИ доступ к
   1С по HTTP/OData; есть ли у Алсеко кабинет/API для ОСИ; в каком виде
   председатель может предоставить выписку Kaspi и **согласна ли** (это
   личный счёт — нужно её явное согласие и понимание, кто увидит данные).

1. «7 налогов» — точный перечень и названия колонок в выгрузке 1С.
2. Нужны ли жителям видимые план/факт по категориям, или только
   ответственному составу (см. Блок 5, publish-флаг)?
3. Один бюджетный год на тенант или несколько версий (утверждённый /
   скорректированный)? По умолчанию — одна активная версия на год.
4. Мультивалютность не нужна (только ₸) — подтвердить.
5. Нужна ли реальная привязка исходящих платежей Kaspi к конкретным
   документам расходов (документооборот), или достаточно списка
   «без документа»?

## Acceptance criteria

- Из файла Excel можно загрузить расходы, 1С, расшифровку УК, Алсеко,
  выписку Kaspi и бюджет — каждый через предпросмотр и с откатом партии.
- Для каждого источника есть коннектор (`API` или `FILE`) со страницей
  «Источники»: статус, время последней синхронизации, ошибки; повторная
  синхронизация не создаёт дублей; учётные данные не попадают в ответы и
  логи.
- Слой сверки выдаёт список расхождений между источниками (минимум
  проверки №1–5) с суммами и ссылками на обе строки; пояснения и закрытие
  расхождений фиксируются в `AuditLog`.
- Сводка план/факт показывает перерасход по категориям и месяцам,
  кварталам и году; итоги совпадают с источниками.
- Отчёт «не расшифровано» перечисляет крупные суммы без полной
  расшифровки и экспортируется как запрос в УК.
- Банковская сверка находит платежи без начисления и выплаты без
  документа; повторная загрузка не создаёт дублей.
- Итоговая xlsx-книга содержит листы бюджета, факта, план-факта, ФОТ,
  Алсеко, сверки, «не расшифровано», кириллица отображается корректно
  (проверить открытием файла, не только размером буфера — как в Task 0022
  и 0032).
- Доступ строго по ролям; жители не видят выписки, зарплаты, сырые
  суммы по контрагентам.
- Все новые таблицы изолированы по `tenantId` (Task 0031 — tenant
  isolation); нет доступа к чужим данным через `:batchId`/`:id`.
- Все записи изменений — в `AuditLog`.
- `npm test` и `npx tsc --noEmit` чистые в `backend/` и `frontend-web/`;
  kk/ru/en i18n parity для всех новых экранов.

## Explicitly out of scope

- Запись в 1С/Алсеко/Kaspi из приложения: интеграции **только на чтение**
  (никаких платежей, проводок и изменений во внешних системах).
- OCR фотографий и сканов документов (заказчик: «фотографий не надо»).
- Начисление и уплата налогов, расчёт зарплаты — только импорт готовых
  данных.
- Автоматическая рассылка запросов в УК/бухгалтеру.
- Переход финансовых полей на `Decimal`.
- Мобильные экраны — аудит остаётся web-only (staff-часть).
